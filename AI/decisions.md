## [DEC-001] 前端框架選型：Next.js 14

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：需要支援 SEO、響應式、多語系（i18n），且未來可能需要 SSR
- **選項**：
  1. Next.js 14（App Router）
  2. Vite + React SPA
  3. Nuxt.js（Vue）
- **決策**：Next.js 14（App Router）
- **理由**：
  - 原生支援 i18n（next-intl）
  - App Router 的 Server Component 可減少前端 bundle 大小
  - Vercel 部署零配置
  - 社群與文件最完整
- **取捨**：App Router 學習曲線較高；比 Vite SPA 架構更複雜

## [DEC-002] 後端與資料庫：Firebase

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：需要 Google OAuth、即時資料更新（通知）、Serverless 函式（計時防作弊、Sheets 同步）
- **選項**：
  1. Firebase（Auth + Firestore + Functions）
  2. Supabase（PostgreSQL + Auth + Edge Functions）
  3. 自建 Node.js API + MongoDB
- **決策**：Firebase
- **理由**：
  - Google OAuth 整合最原生（Firebase Auth）
  - Firestore 即時監聽適合通知與排行榜更新
  - Firebase Functions 可執行計時驗證、Sheets 同步等後端邏輯
  - 免費額度（Spark Plan）足夠 MVP 測試
- **取捨**：Firestore 非關聯式資料庫，複雜查詢（如跨 collection JOIN）需在應用層處理；Cold Start 延遲約 500ms-1s

## [DEC-003] 樣式方案：Vanilla CSS + CSS Modules

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：像素風格需要高度客製化的樣式，包含 `image-rendering: pixelated`、像素字型、逐格動畫
- **選項**：
  1. Vanilla CSS + CSS Modules
  2. TailwindCSS
  3. styled-components（CSS-in-JS）
- **決策**：Vanilla CSS + CSS Modules
- **理由**：
  - 像素風格的細節控制（動畫 steps、像素邊框）用 utility class 難以表達
  - CSS Modules 提供 scoped 樣式，避免命名衝突
  - 無額外 runtime 負擔
- **取捨**：樣式撰寫速度較 Tailwind 慢；需自行維護設計 Token

## [DEC-004] 計時機制：伺服器時間為主

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：每題有倒數計時，若以前端時間為準，考生可透過修改系統時間作弊
- **選項**：
  1. 純前端計時（localStorage 記錄開始時間）
  2. 伺服器時間：開始時記錄 `startedAt`，提交時由 Firebase Function 驗證剩餘時間
- **決策**：伺服器時間驗證
- **理由**：確保計時公平性，與業務規則一致
- **取捨**：每次提交需一次 HTTP 呼叫驗證，有輕微延遲；網路不穩時需做離線處理（暫存答案，恢復連線後補送）

## [DEC-005] 題庫同步：手動觸發

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：題庫來源為 Google Sheets，需決定同步頻率
- **選項**：
  1. 手動觸發（主管點擊「同步題庫」）
  2. 每日定時同步（Firebase Scheduler）
  3. 即時同步（Sheets webhook）
- **決策**：手動觸發
- **理由**：
  - 題庫異動頻率低，不需要自動化
  - 主管對同步時機有明確掌控，避免考試進行中題庫突然變動
  - Google Sheets webhook 設定較複雜，MVP 不需要
- **取捨**：主管需記得手動同步；若忘記同步，新題目不會出現在考試中

## [DEC-006] 申論題並行限制：同時只能一場

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：申論題需要主管人工批改，若允許多場並行，主管工作量難以管理
- **決策**：同一考生的申論題同時只能存在一場（含待批改狀態）
- **理由**：簡化批改流程，確保考生認真對待每次申論
- **取捨**：若主管批改緩慢，考生可能當月無法完成「每月至少一次」的要求；需提醒主管及時批改

## [DEC-007] 排行榜計分：最高分制

- **日期**：2026-07-28
- **狀態**：✅ 已採用
- **背景**：綜合模式可無限刷題，需決定排行榜的代表分數
- **選項**：

## [DEC-008] 綜合模式問答題改由主管批改與排行榜採計規則

- **日期**：2026-08-17
- **狀態**：✅ 已採用
- **背景**：原綜合模式問答題採自動關鍵字/標點符號比對，但問答題文字難以對焦精準正確性，易造成誤判或公平性爭議。
- **選項**：
  1. 繼續使用文字比對並維持即時算分。
  2. 綜合模式問答題改由主管於 `/admin/grade` 人工批改，待批改完成後才結算總分。
- **決策**：選擇選項 2，且未批改完畢前，考卷採 **方案 A（暫不寫入排行榜）**。
- **理由**：
  - 確保客服問答實務觀念的審核精準度與專業性。
  - 考生交卷後即時獲得「選擇題分數」，問答題由主管審核完成後再計入總分與通過與否判定。
  - 防範未經主管確認的分數提前刷入排行榜造成名次波動。
- **取捨**：
  - 綜合模式分數不再全自動即時結算。
  - 需延展 `/admin/grade` 批改後台介面，支援綜合模式問答題打分。
  - Google Sheets 成績匯出調整至主管提交評分時觸發。

## [DEC-009] 客服人員離職狀態管理與生效月份統計與批改過濾機制

- **日期**：2026-09-01
- **狀態**：✅ 已採用
- **背景**：同仁離職後，若仍持續顯示在主管批改後台或當月份團隊考核總覽中，會干擾主管批改與考核進度評估。
- **決策**：
  1. 於 `/admin/settings` 新增客服考生狀態管理（`🟢 在職` / `🔴 已離職`），並允許設定離職生效月份 (`YYYY-MM`)。
  2. 主管批改後台 (`/admin/grade`)：一律隱藏 `status === 'resigned'` 的離職同仁考卷（包含待批改/已批改/已擱置）。
  3. 團隊考核狀況與進度總覽 (`/admin/users`)：若離職生效月份 <= 統計選定月份，於該選定月份列表中自動隱藏該員；選擇離職前歷史月份則保留過往完整紀錄。
- **理由**：
  - 避免主管浪費時間批改已離職同仁的考卷。
  - 保留歷史考卷數據的同時，維護當月考核與統計的潔淨度。

## [DEC-010] 登入 Session 級別持久化與關閉頁面自動登出機制

- **日期**：2026-09-01
- **狀態**：✅ 已採用
- **背景**：Firebase 預設採用持久化紀錄，導致同仁關閉分頁或瀏覽器後隔週再次開啟時仍處於登入狀態，無法精準捕捉同仁的登入活動時間。
- **決策**：
  1. AuthContext 配置 `browserSessionPersistence` (Session 級別持久化)，並移除 Cookie 的長時效 `max-age`。
  2. 搭配 `sessionStorage` 進行分頁生命週期驗證：當偵測到全新開啟的分頁/視窗時，主動清除快照要求重新登入。
  3. 每次同仁完成登入時，自動更新 `users` 集合的 `lastLoginAt` / `lastActiveAt` 時間戳記。
- **理由**：
  - 確保「最近活動時間」能夠在客服同仁每次開啟網站登入時實時精準刷新。
  - 提高帳號使用安全性。

## [DEC-011] 歷次成績記錄、團隊考核與排行榜切分月份下拉選單

- **日期**：2026-09-01
- **狀態**：✅ 已採用
- **背景**：當同仁刷題紀錄較多時，跨月份歷史資料混在一起，導致主管與同仁難以查閱特定月份的表現。
- **決策**：於冒險排行榜 (`/leaderboard`)、團隊考核總覽 (`/admin/users`)、主管批改後台 (`/admin/grade`) 與個人歷次成績與錯題記錄 (`/profile/results`) 全面新增「📅 月份選擇」下拉選單，預設切換至當月 (`YYYY-MM`)。
- **理由**：提升大數據量時的檢視效率，落實按月考核與按月結算排行榜之目標。

## [DEC-012] 錯題回顧評分標示細化與直達歷次成績導覽

- **日期**：2026-09-01
- **狀態**：✅ 已採用
- **背景**：問答題非滿分（如 3/5 分）時，原本錯題回顧左側列表一律顯示「已評分」，容易讓考生誤以為獲得滿分。
- **決策**：
  1. 將問答題得分標示細化為：`💯 滿分 (5分)`、`⚠️ 部分得分 (X/5分)` 與 `❌ 0分`。
  2. 修正篩選按鈕為 `需檢討/非滿分 (X)`，將選擇題答錯與問答題非滿分項目一併納入檢討專區。
  3. Navbar 新增 `📊 歷次成績與錯題記錄` 直達導覽按鈕。
- **理由**：精準反饋檢討重點，並縮短考生於評分完成後查閱歷史軌跡的操作路徑。
